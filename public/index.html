Vektor Flow

Vektor Flow (VKF) is an experimental compiled language for calculations, data and visual programs. You describe a flow of typed values; the compiler works out their concrete types, shapes, storage and a safe way to execute the flow.

The core: values flowing through scopes

Scopes produce values

VKF is built from values, functions and scopes rather than a large vocabulary of special statements. An indented scope produces its final value, and a complete scope can become a record. A calculation, a branch and a small data object therefore share one model.

That becomes useful when a formula grows into a process. A physics step can keep intermediate quantities local and return the next state. A data-cleaning stage can expose its result without leaking temporary names. A graphics description can assemble coordinates, material properties and time-dependent values without introducing a hierarchy of builder classes.

Rust and languages in the ML family also allow blocks or expressions to return values. VKF’s difference is that scope also participates directly in assembling records, modules and callable results.

Typed without annotation noise

Every VKF value has a compile-time type. An annotation can state a public contract, but it is not required on every binding, parameter or result. When the program provides enough evidence, the compiler infers those types as well as record fields, vector element types and relationships between fixed shapes.

This gives exploratory numerical work a light surface while keeping library boundaries precise. A local transformation can omit redundant annotations; a solver can still require an exact numeric shape and reject an incompatible call before the program runs. The open type placeholder is another compile-time inference tool, not a dynamically typed box.

F# and Haskell offer the closest familiar lesson: omitted annotations do not make a language dynamically typed. VKF applies the resulting facts to vector shape, overload selection and direct storage layout as well as ordinary type checking.

One function can flow through vectors

Vector application is a core call rule, not a separate collection framework. A function written for one compatible value may be applied through vector layers, including nested vectors, while preserving the result shape. When a function explicitly accepts the complete container, that exact match wins. Records and tuples stay atomic, so the compiler does not hunt through fields for something that happens to fit.

The same calibration can consequently serve one sensor, a row of sensors or a batch of rows. A force law can serve one particle or many particles. The mathematical rule stays in one function instead of being copied into scalar and array versions.

Julia makes elementwise calls explicit with dotted broadcasting. APL and J use array rank, while NumPy broadcasts positional dimensions. VKF combines automatic recursive call lifting with static overload priority and named indices: shared axis names align, and unmatched names broadcast. Those ideas have relatives, but their integration into an ordinary typed call is distinctive.

Change is explicit

VKF is value-oriented and makes change visible. Declaring a name and updating an existing name are different operations, so a misspelling cannot silently create state and an ordinary expression cannot conceal reassignment. Generated code unwinds owned strings and containers when control leaves a function or an error propagates.

VKF is not purely functional. Explicit aggregate updates preserve alias identity, and capabilities such as interface arenas are deliberately mutable. The useful rule is therefore not that nothing can ever change; it is that change is marked, scoped and separated from ordinary value flow. This sits between the persistent value style of Clojure or F# and the explicitly mutable style encouraged by Rust.

Control flow needs no keywords

Conditions, matching, loops, early return, assertions and typed error handling are expressed with operators and indentation. There are no if, else, while, catch or finally keywords. A one-sided false condition yields null. A multiway match uses ordered arms and an ordinary final arm as its fallback, rather than a special else form.

Ordinary owned values also need no user-written finally path: generated unwinding releases them. Observable effects keep their defined order, while external resources remain governed by the capability that owns them. This is helpful when control flow belongs inside a calculation—validation can stop early, a match can return its result directly, and recovery can stay beside the expression that may fail.

APL and J demonstrate the reach of symbolic operations, while Lisp demonstrates the power of a small structural core. VKF is neither an APL dialect nor a Lisp. No individual ingredient above is unprecedented; the unusual part is their combination in a keyword-free, indentation-based, statically inferred language.

How VKF compiles the flow

The compiler settles what a program means before choosing how to execute it. That separation matters because a call can imply overload selection, type inference, vector lifting, ownership and an eventual execution policy. Those decisions belong to compilation, not to a dynamic dispatcher in the generated program.

The main path is VKF source → canonical typed IR → machine IR → target artifact.

  1. The frontend parses scopes and calls, resolves names and overloads, infers omitted types and shapes, and records the selected operations in canonical typed IR. At this point an automatically lifted call already has an exact vector path, while tuples and records remain explicit whole values.
  2. Lowering turns that semantic program into target-neutral machine IR. Layouts, ownership transfers, ordered effects, dependencies and error paths are made explicit so a backend does not need to rediscover language meaning.
  3. Optimisation can specialise generic and lifted calls, remove unreachable work and unnecessary copies, and consider inlining, fusion, SIMD or a safe parallel plan. Every transformation must preserve the same observable program; an attractive timing is not permission to change a result.
  4. A direct backend selects instructions, creates relocations and writes PE for Windows, ELF for Linux, Mach-O for macOS, or WebAssembly bytecode. The installed native path does not invoke a C++ compiler, assembler or separate linker for each user program.

Concrete facts survive all the way through this path. A fixed vector shape can become an exact stack or aggregate layout, and a lifted scalar function can become statically selected calls or a direct loop instead of runtime type inspection. Dynamic containers carry explicit layout and ownership information, which lets the compiler reuse storage or remove a copy only after lifetime and alias analysis prove that doing so is safe.

Optimisation is evidence-bearing rather than a blanket promise. For an eligible x64 program, version 0.4.5 can train the 256-policy landscape independently for each canonical function. A candidate is emitted in the complete program and checked against the baseline's exact output before its function proof is kept; the combined set of winners receives a separate composition receipt. Repeated compilation can reuse a receipt only when the function, its dependencies, the program composition, target, host and toolchain still match. Ineligible or effectful programs keep a conservative production policy instead of being replayed merely to search for a faster timing.

Typed layout does not imply hashing. The current published language does not promise that arbitrary vectors are hash keys. Multisets use supported uniform scalar keys, and statically named maps lower to typed records, so ordinary vector arithmetic pays no whole-vector hashing cost.

The implementation is also partway through a staged bootstrap. The repository retains a broad C++ Stage 0 as the semantic oracle while direct coverage expands one tested language slice at a time. Unsupported strict-direct input fails clearly instead of silently changing meaning. The intended fixed point is a self-hosted compiler rebuilt from a versioned VKF seed; the current boundary and cutover rules are recorded in the compiler architecture.

Lazy and parallel, without source machinery

The execution model begins with one deterministic serial meaning. Authors should not need worker pools, futures, joins, device objects or chunk sizes for ordinary work. Where semantics permit it, the implementation may keep a demand-backed vector as a descriptor, fuse adjacent operations, use SIMD, run independent regions on multiple cores, or choose a supported GPU plan.

Demand matters when computing everything would be wasteful: a chart may need only its visible range, a preview may sample a field, and a simulation may have independent expensive results. Parallelism matters only when its overhead is smaller than the saved work. VKF can require both a safety proof and a measured win before retaining a parallel candidate.

Effects still commit in order. Fallible work preserves error order. A numeric reduction cannot be reassociated merely because more cores are available. These constraints let scheduling change without changing what the program observes.

Haskell makes laziness a broad evaluation rule, Clojure provides lazy sequences, and libraries such as Rayon expose convenient parallel work explicitly. VKF’s direction is different: demand and scheduling are private choices beneath the same source program. In the current release that direction is conservative, not universal—pipes are eager, not every vector is demand-backed, and verified automatic CPU parallelism accepts only proven shapes. The execution notes separate implemented support from the larger design.

Compilers for native systems and WebAssembly

Published packages cover Windows x64, Linux x64 and macOS ARM64, with portable archives as well as platform installers. They can compile command-line tools, standalone calculations, test suites, numerical kernels and native visual programs on the machine where they will run.

The WebAssembly package brings the compiler and supported runtime into a browser or another WASM host. The documentation uses it to compile examples locally in a disposable worker—there is no compilation server. The same approach can support interactive lessons, embedded calculators, reproducible demonstrations and client-side visual tools. Browser programs intentionally receive no direct filesystem, process, network, DOM or localhost access; visual output crosses a validated compiler-owned interface instead.

These are the three currently published native target families plus WebAssembly, not a claim that every processor and operating system is already supported. Use the page-wide release selector to keep downloads, browser compiler and measured evidence on the same version.
